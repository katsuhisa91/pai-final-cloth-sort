# 番号付き布片の仕分け — Physical AI 応用編1 最終課題

手書きの番号が書かれた 5 cm 角の布片を、番号どおりの置き場へ運ぶロボットのパイプラインです。
「撮影 → 布片の検出 → 番号の読み取り(自前学習した CNN) → 計画 → pick & place → カメラで検証」を
dora-rs の dataflow としてつなぎ、MuJoCo の物理シミュレーション上で Franka Panda を動かしています。
布は変形体(MuJoCo の flex)で、2 本指ハンド(ゴムパッド付き)でつまむ把持そのものを物理に任せています。

- 提出動画: `runs/submission/PAI最終課題_katsuhisa91.mp4`(2 分 54 秒、1920x1080。説明スライド + 学習した方策(ACT)でアームを動かした仕分けの実行(単一プロセス版、2 倍速、画面に明記))
- 実行部分のみ: `runs/cloth8/cloth_sort.mp4`(単一プロセス版、seed 4、等速)。学習した方策で同じ場面を回した動画は `runs/cloth8_act/cloth_sort.mp4`。dora 版の実行は `./run_dora.sh` で `runs/dora/frames` に出る(同じ seed で搬送中の落下が 4 枚。把持の成否は物理の微小な差で変わる)
- 報告書: `report/report.pdf`(元は `report/report.html`)
- 提出の流れ(public 化、YouTube、omnicampus): `SUBMISSION.md`
- 実機は未接続。アームは `RobotArm` インターフェースの MuJoCo 実装(`GripperArm`)で、実機対応はこの 1 クラスを足す形
- 3 つのバックエンドを切り替えられる: `cloth`(変形体の布 + 2 本指、既定)/ `mujoco`(剛体の布片 + 吸着の模擬)/ `2d`(自前の 2D、軽量)
- アームの動かし方は 2 通り: 手続き的な把持(状態機械 + IK、既定)と、それを教師に模倣学習した方策(LeRobot の ACT、`--arm policy`)。詳しくは「学習した方策でアームを動かす」

## 動かし方

```sh
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -r requirements.txt
export PYTHONPATH=$PWD

# 1. 番号読み取りモデルを学習(合成データ、CPU で 5 分程度)
.venv/bin/python -m cloth_sort.ml.train --out models

# 2. 単一プロセスで実行し、フレームと動画を作る(ffmpeg が必要)
.venv/bin/python -m cloth_sort.pipeline --backend cloth --seed 4 --n 8 --out runs/cloth8 --video    # 変形体 + 2 本指(30 分ほど)
.venv/bin/python -m cloth_sort.pipeline --backend mujoco --seed 4 --n 12 --out runs/mj4 --video    # 剛体 + 吸着(2 分ほど)
.venv/bin/python -m cloth_sort.pipeline --backend 2d --seed 1 --n 12 --out runs/seed1 --video      # 2D(数秒)

# 3. dora-rs で分散実行(sim / brain / recorder の 3 ノード。既定は cloth)
./run_dora.sh
./run_dora.sh graph     # 構成図

# 4. 提出用の動画(スライド + 学習した方策での実行の録画、実行部分は 2 倍速)を作る
.venv/bin/python tools/make_submission_video.py --run-video runs/cloth8_act2/cloth_sort.mp4 --log runs/cloth8_act2/log.jsonl \
  --summary runs/cloth8_act2/summary.json --fig runs/cloth8/top_detect.png --run-speed 2 --arm policy

# テスト
.venv/bin/python -m pytest -q
```

MuJoCo の描画は OpenGL(macOS では CGL)を使うので、描画が必要なコマンドはサンドボックス等で
ウィンドウサーバに繋げない環境だと失敗します。物理計算とテストは描画なしで動きます。
手書き風フォントは macOS のものを使います。Linux(CI など)では DejaVu / Liberation で代用するので、
テストは通りますが、報告している読み取り精度は macOS のフォント構成での値です。

## 設計の要点

- 既定の構成で学習しているのは番号読み取りの 1 文字 CNN。検出(背景差分)・計画(しきい値と貪欲法)はルール。把持の手順・アーム制御は、手続き的な版(状態機械 + IK + 位置サーボ)と、それを教師に模倣学習した版(ACT。「学習した方策でアームを動かす」節)を切り替えられる
- AI が見るのは机の真上の俯瞰カメラ 1 台だけ。動画左下の手首カメラは可視化用(提出動画の録画時点ではハンドに追従する仮想カメラ。コードは手首固定のカメラに改めた)

- 読み取りは「1 文字 CNN + 連結成分で文字分割」。語彙は 0〜9 と「-」なので、学習で見ていない番号(例: 1-2)も読める
- 確信度がしきい値未満の布片は止めずに要確認トレイへ逃がす。誤った置き場に置くより、人が後で見るほうが安い
- 置いた直後にアームを視野外へ退避させ、カメラで読み直して計画と照合する(自己検証)。読み直しの確信度が低いものは NG ではなく「要確認」。ログは JSONL で残し、再学習データの種にできる
- ロボット側(sim)と AI 側(brain)を別プロセスに分け、dora の Arrow メッセージで接続。実機化はロボット側だけの差し替え
- MuJoCo 版のアームは、ツール先端の目標位置と向き(真下)からヤコビアンの減衰最小二乗で関節角を解き、位置サーボ(重力補償つき)で追従させる。目標点は速度制限つきで動かす
- 布は MuJoCo の flex(2D シェル、9×9 格子、厚さ 3 mm、ヤング率 1e5 のフェルト程度)。重力・接触・曲げは物理計算
- 把持は Panda の 2 本指ハンド + ゴムパッド(摩擦 2.0)で、物理に任せる。平らに置かれた布を平行グリッパでつまむために、左指のパッドを 2.5 mm 長い「唇」にして机面まで押し込み、閉じる間はハンド全体を動かして押さえ側の指を世界に対して止める(折り目が押さえ指の前で立ち、2 枚重ねでつままれる)。持ち上げ 3 cm/s、搬送 6 cm/s を超えると抜ける
- 置くときは置き場の上で放して落とす。布は折れて落ちるので番号は読み直せず、置いた後の検証は「置き場の領域に布があるか」を背景差分で確かめる方式に変えた。つかみ損ねは撮り直して最大 2 回再試行し、搬送中に落としたら失敗として人に回す
- 剛体 + 吸着版(`--backend mujoco`)も残してある。こちらは置いた後に番号を読み直す検証ができる

## 学習した方策でアームを動かす(模倣学習)

手続き的な把持は「つまむ点から 25 mm 縁へ寄せる」「閉じながらハンドを 18 mm ずらす」「3 cm/s で持ち上げる」といった
手で決めた数値の集まりで、ロボットの動き方そのものは AI ではありませんでした。
そこで、この手続きを教師にして「目標が与えられてから、つまんで運んで放すまで」を LeRobot の ACT(Action Chunking Transformer)に
模倣学習させ、`--arm policy` で差し替えられるようにしています。上位(検出・読み取り・計画・検証)と下位(IK + 位置サーボ)はそのままです。

| | 内容 |
|---|---|
| 観測 | 俯瞰カメラ 256×128、手首カメラ 256×128、状態 8 次元(手先 xyz、指の開き、目標 = つまむ点 xy と置く点 xy) |
| 行動 | 手先の目標位置 xyz [m] + 指の指令(0 閉〜1 開)、20 Hz。100 ステップ(5 秒)ぶんをまとめて予測し、時間方向に平均して使う |
| 教師 | `GripperArm` + `PickPlace`(手続き的な把持)。布 1〜3 枚の場面(残りは仕分け途中を模して置き場にも置く)で 1 枚を運ぶ |
| データ | 154 エピソード収集、成功 123(うちつかみ直して成功 13)を使用、51,131 フレーム。LeRobot データセット v3(parquet + AV1 動画) |
| 学習 | `lerobot-train`、ACT 既定構成(ResNet18 ×2、dim 512、chunk 100、VAE あり)、52M パラメータ、20,000 ステップ、batch 16、Apple M1 Pro の MPS で約 1 時間 45 分 |
| 評価 | 学習に使っていないシード(20000〜)で、学習した方策と教師を同じ場面で比べる(下表) |

評価結果(学習に使っていない 20 場面、seed 20000〜20019。同じ場面で両者を走らせた)

| | 学習した方策(ACT、20,000 ステップ) | 教師(手続き的な把持) |
|---|---|---|
| 目標の ±50 mm に置けた | **14 / 20** | 12 / 20 |
| 両方成功 / 方策だけ成功 / 教師だけ成功 / 両方失敗 | 9 / 5 / 3 / 3 | |
| 1 枚あたりの所要(シミュレーション時間の平均) | 23.6 秒 | 19.3 秒 |
| 時間切れ(45 秒) | 0 | - |

学習の途中経過(同じ 8 場面、seed 20000〜20007): 5,000 ステップ 2/8 → 10,000 ステップ 3/8 → 15,000 ステップ 4/8 → 20,000 ステップ 5/8(教師は同じ 8 場面で 5/8)。
方策の失敗は、つまめずに空で運ぶものと、置く位置が目標から 5〜6 cm ずれるもの(置き場の半ピッチを超える)の 2 種類でした。
教師の失敗は搬送中の落下が主で、把持そのものが物理の微小な差で揺れるためです。模倣学習の方策が教師を 2 本上回ったのは、
把持の成否が確率的なぶんの揺れの範囲で、「方策が教師より上手い」とまでは言えません(20 場面での差)。
評価の記録は `runs/eval/act_020000/`(JSONL。動画はリポジトリに含めていない)。

仕分けのパイプライン全体(seed 4、8 枚、検出 → 読み取り → 計画 → 方策で搬送 → 検証)を学習した方策で回した結果は `runs/cloth8_act/`(動画 `cloth_sort.mp4`、`log.jsonl`、`summary.json`):
置き場へ 6 枚(存在確認 OK 6)、誤配置 0、失敗 2(いずれも要確認トレイ行きの 2 枚。トレイはロボット側の机の縁にあり、学習データの 15% しか無かった行き先)、202 秒。
同じ seed の手続き的な把持は置き場 5 枚 + 要確認 3 枚で失敗 0(再試行 4 回)でした。8 枚の机は学習時(1〜3 枚)より混んでいますが、置き場への搬送は 6/6 で通りました。
改善後の実行器(再試行・振り落とし・開ループ・補正)で同じ場面を回し直すと、置き場 5(検証 OK 5)+ 要確認 2 の **7/8**、失敗 1(番号 3、2 回つかみ直しても置けず)、235 秒でした(`runs/cloth8_act2/`)。トレイ行きの 2 枚は両方成功しています。

### 成功率を上げる取り組み(2 回目)

20 場面で 14/20 だった方策を、失敗の原因ごとに手を打って 19/20 まで上げました。手順と結果は次のとおりです。
方策の中身は同じ(v1、20,000 ステップ)で、変えたのは方策の外側(実行器)です。

| 手 | 内容 | 20 場面の成功 |
|---|---|---|
| 元 | v1 の方策をそのまま実行 | 14 / 20 |
| 再試行 | 置けていなければ撮り直して最大 2 回やり直す(手続き版と同じ立て直し) | 13 / 20(再試行が効く「空で運ぶ」失敗がこの 20 場面には少なかった) |
| 放し方 | 指を全開にしても布がパッドに引っかかって宙に残る失敗が 2 件(教師にもある)。接触が残っていれば横に 3 cm 振って落とす。教師と方策で共通の `release_step` | 引っかかり 2 件を回収 |
| 終了の判定 | 方策の指の指令が中途半端(7 割開き)でも、布が指から離れて置く点の近くで机に載ったら(接触なし・布が低い)放し終わりとみなす。指令のしきい値だけだと時間切れになっていた | 時間切れを除去 |
| 時間平均をやめる | ACT の temporal ensembling(毎周期、過去の予測と平均)は、絶対位置の指令を平均するせいで手先が 1〜2 mm/周期しか進まない「這う」状態に入り、長い搬送で時間切れになった。100 ステップ(5 秒)の予測をそのまま実行し 5 秒ごとに観測し直す開ループ実行に変更 | 15 / 20 |
| 系統誤差の補正 | 教師は目標の ±3 mm に落とすのに、方策は進行方向に 22 mm(sd 15)止まり遅れる。評価とは別の 20 場面(seed 21000〜)で測り、方策に渡す置く点をその分だけ手前にずらす(キャリブレーション) | **19 / 20**(較正用の 20 場面は補正前でも 20/20) |

残る 1 件は要確認トレイ行きで、v1 の学習データでは 15% しかなかった行き先です。

方策そのものを良くする手も試しました(結果は下)。

- **教師の上限**: 教師の失敗はほぼすべて搬送中の落下です。接触数のしきい値 6 → 10、搬送を 4 cm/s、持ち上げ後に 0.5 秒待つ、の 3 つを 16 場面で比べましたが差はありませんでした(元 14/16、各 14・13・13)。`tools/teacher_variants.py`
- **データ倍増 + 相対状態(run 2)**: トレイ行きを 30% にして 400 本収集(成功 326 本・134k フレーム)、状態に「目標 − 手先」を足した 12 次元で 40,000 ステップ。同じ実行器(再試行・振り落とし・開ループ・補正 22 mm)で評価 20 場面 **18/20**、較正用 20 場面 **20/20**(v1 は 19/20 と 20/20)。止まり遅れは 25 mm のままで、相対状態では消えなかった。要確認トレイ行きの弱さは改善(較正用の 4 件を全部成功)
- **外乱つきデモ(DART、run 3)**: 接近・搬送・退避の間だけ手先目標に 1 cm の外乱を足して動かし、記録する行動は教師のきれいな指令のまま。方策が少しずれた状態からの戻り方を学ぶ。160 本収集(成功 126 本)し、run 2 のデータと合わせた 452 本・186k フレームで 40,000 ステップ。評価 20 場面 **19/20**、較正用 20 場面 **19/20**。残る 2 件はどちらも目標から 54 mm(許容 50 mm)の惜しい外れ

3 つのモデルを同じ実行器で比べると、どれも 40 場面中 38〜39(95〜97%)で差はありません。成功率を 14/20 → 19/20 に上げたのは方策の外側(再試行・振り落とし・開ループ実行・終了判定・系統誤差の補正)で、データを 4 倍にしても成功数は変わりませんでした。

| モデル | 学習データ | 評価 20 場面 | 較正用 20 場面 |
|---|---|---|---|
| v1(ACT、20k ステップ) | 123 本 | 19 / 20 | 20 / 20 |
| v2(相対状態、40k) | 326 本 | 18 / 20 | 20 / 20 |
| v3(相対状態 + DART、40k) | 452 本 | 19 / 20 | 19 / 20 |

残る失敗は「目標から 5 cm 強ずれて落ちる」近接外れです。置き場のピッチ 10 cm に対して許容 ±5 cm なので、布が隣の置き場に入ることはありませんが、置き場の中心からは外れています。
これ以上は、置く直前に手首カメラで置き場の枠を見て位置を合わせる(視覚サーボ)か、教師の置き方そのもの(つまんだ布を落とす)を変える必要があります。
- **事前学習済み VLA の微調整(SmolVLA)**: `lerobot/smolvla_base`(SO-100 の公開データで事前学習、450M)を run 3 のデータで微調整(視覚エンコーダは固定、行動側 100M を学習、batch 8、4,000 ステップ、M1 Pro で約 3 時間)。同じ実行器で評価 20 場面 **0/20**、較正用 20 場面 **4/20**。つまむところまでは行くが、搬送中に落とすか置き場の手前で止まる。公開データの事前知識はこの把持(mm 単位の唇の押し込み)には効かず、この学習量では ACT に届かなかった。`.venv-vla`(`lerobot[smolvla]`)で再現できる

データセット(135 MB)と学習済みモデル(約 200 MB)はリポジトリに含めていません。上のコマンドで再現できます。

### Hugging Face に上げる場合

再学習(1 時間半〜2 時間)なしで試せるように、モデルとデータセットを Hugging Face Hub に置いてあります(2026-10-17 時点で private)。

- モデル: https://huggingface.co/katsuhisa91/pai-cloth-sort-act(ACT v1、評価 20 場面で 19/20 を出した実行器の既定と同じ設定で読める)
- データセット: https://huggingface.co/datasets/katsuhisa91/cloth_pickplace(123 本)、https://huggingface.co/datasets/katsuhisa91/cloth_pickplace_v3(452 本、DART 込み、相対状態 12 次元)

上げ直す手順(`hf auth login` 済みが前提):

```sh
# モデル(学習済み ACT。config.json + safetensors + 前処理の定義)
.venv-il/bin/hf upload katsuhisa91/pai-cloth-sort-act runs/train/act/checkpoints/020000/pretrained_model --private
# データセット(LeRobot v3 形式。LeRobotDataset が読めるようバージョンタグも付く)
.venv-il/bin/python -c "from lerobot.datasets.lerobot_dataset import LeRobotDataset; \
  LeRobotDataset('katsuhisa91/cloth_pickplace', root='data/cloth_pickplace').push_to_hub(private=True)"
```

上げたあとは `--policy katsuhisa91/pai-cloth-sort-act`、`--dataset.repo_id=katsuhisa91/cloth_pickplace`(`--dataset.root` なし)で参照できます(private の間はアクセス権のあるトークンでログインしておく)。
提出時に public にする場合は `--private` を外すか、Hub の設定で公開にします。

### 公開されているロボットデータとの関係

布を扱う実機データは Hugging Face に多数あります(LeRobot 形式のもの: `lerobot/aloha_static_towel`(ALOHA、タオルたたみ 50 エピソード)、
`lerobot/unitreeh1_fold_clothes`(Unitree H1、38 エピソード)、`lerobot/usc_cloth_sim`(Franka のシミュレーション、1,000 エピソード。
行動は xyz の目標 + グリッパで本リポジトリと同じ形)、ほか SO-100 / SO-101 / Piper / Unitree G1 のタオルたたみが数十件)。
ただしロボット・カメラ・場面がすべて違うので、そのまま本リポジトリの Panda を動かす学習データにはなりません。
使うなら「それらで事前学習された VLA(SmolVLA、π0、GR00T など)を土台に、本リポジトリのデモで微調整する」形になります。
今回は Mac 1 台で回せる範囲として、自前のシミュレータで集めたデモから ACT を学習しました。

### 「置く」から「きれいに置く」へ(敷き置きの学習)

落とす置き方では、布は折れたうえに裏返って着地します(数場面で確認: 面積比 0.6 前後、裏向き)。番号は読み直せません。
落とす教師を真似る限り方策も落とすだけなので、まず教師に「敷く」動作を足しました。

- 敷き方: ぶら下がった布の下端が机に触れる高さから、ロボット側へ 12 cm 進みながら机まで 4.6 cm 降りる。下端が机との摩擦で留まり、布は手の後ろに順に敷かれる(ベルトコンベアの要領)。進む向きが逆だと布が裏返る
- 「きれい」の基準: 目標 ±50 mm に載る、頂点の高さの幅 ≤ 8 mm(平ら)、凸包の面積が布の 80% 以上(広がっている)、表向き。さらに俯瞰カメラで番号を読み直せるかも測る(`env.neatness()` / `neat()`、評価の `neat` / `reread_ok`)
- 試してだめだった敷き方: 斜めに降ろす(布がまとまる、面積比 0.2)、机まで降ろしてから低く引く(折れた部分が一緒に滑る)

教師の敷き置きで 200 本集め(成功 177、きれい 95)、ACT を 30,000 ステップ学習しました(`--place lay`、`runs/train/act_lay`)。同じ 20 場面の結果:

| | 置けた | きれい(平ら・広がり・表向き) | 番号を読み直せた |
|---|---|---|---|
| 敷き置きの教師 | 14 / 20 | 10 / 20 | 5 / 20 |
| 敷き置きを学んだ方策 | 8 / 20 | 3 / 20 | 1 / 20 |
| 落とす方策(参考) | 19 / 20 | 0(落とすと裏返る) | 0 |

置けたものは方策も教師も全部表向きで、面積比は方策 0.76・教師 0.85 でした。敷く動きそのもの(進みながら降りる)は方策も真似できていますが、
置ける率が 8/20 と落とす方策(19/20)より大きく下がりました。敷く動作は手先の高さを mm 単位で合わせる必要があり、落とすより学習が難しいためです。
番号の読み直しが教師でも 5/20 なのは、つまんだ縁の角に番号が来ると、その角が折れ込んで隠れるためです(番号の位置は布ごとにランダム)。

次の一歩は、(1) 教師のきれいな成功だけ(95 本)で学習する、(2) 番号のない縁をつまむ(俯瞰画像で番号の位置が分かっている)、(3) 敷いた後に平らかを見て敷き直す、です。

### 別の物理エンジン(Genesis)を試した結果

布の物理を MuJoCo の flex 以外でも見るため、講義で名前の挙がった Genesis(1.4.4、PBD の布)を Mac(M1 Pro、CPU バックエンド)で試しました(`.venv-genesis`)。
5 cm 角の布を落とし、縁の粒子を動く箱に固定して持ち上げ・搬送・低く引いて敷く・放す、までは動きましたが、

- 速度: 0.5 秒ぶんの落下に 236 秒、10.8 秒ぶんの操作に 2 時間 35 分(実時間の約 900 倍)。MuJoCo flex は同じ Mac で実時間の 2〜15 倍
- 布: 既定の布メッシュは粒子 21 個で、持ち上げても垂れ下がらず板のまま。細かいメッシュにすればさらに遅くなる
- 把持: 粒子をリンクに固定する方式しかなく、指とゴムの摩擦でつまむ物理は扱えない

Genesis は GPU(CUDA)前提の設計で、この環境では比較実験に使える速度ではありませんでした。
布の物理の忠実度を上げる現実的な道は、MuJoCo flex の格子を細かくし自己接触を入れる(計算は数倍遅くなる)か、CUDA のある機械で Genesis / Isaac Lab を使うことです。

### シミュレータの真値を使っている箇所(実機ではセンサに置き換えが要る)

画像・ロボットの動き・布の変形・把持はすべて MuJoCo の物理計算と描画です。作り物の映像や、物理を通さずに布を動かす処理はありません。
ただし実行時の判断のいくつかは、実機では直接は得られないシミュレータの真値(布の頂点座標、ゴムパッドと布の接触数)を読んでいます。

| 判断 | 使っている真値 | 実機での置き換え |
|---|---|---|
| つまめたか・搬送中に落としたか(手続き版) | ゴムパッドと布の接触数、布の高さ | 指の力センサ、グリッパの開き幅、手首カメラ |
| 指に布が残っているか(振り落とし) | 接触数、布の高さ | 手首カメラ |
| 方策の放し終わり・置けたかの判定 | 布の頂点座標と接触数 | 俯瞰カメラで置き場を撮る(パイプラインの検証と同じ) |
| つかみ損ねたときの再試行の要否 | 布の重心 | 俯瞰カメラ(位置の取り直しは既にカメラ) |
| 評価の採点(置けた・きれい・どの布か) | 布の頂点座標、布の正解番号 | 採点用なので実機では人が見る |

方策そのものへの入力(俯瞰カメラ・手首カメラの画像、手先位置、目標)は実機でも得られるものだけです。
評価スクリプトでは、つまむ点に検出結果ではなく布の重心の真値を渡しています(パイプラインでは俯瞰カメラの検出結果)。

### 限界と正直な注記

- 方策が学んだのは「与えられた目標へ、教師と同じ手順で動く」ことで、どの布をどこへ運ぶかは依然として上位のルールが決めます
- 教師が手続きなので、方策の上限は教師の成功率です(教師を超える手は模倣学習では出ません)
- 訓練分布は布 1〜3 枚の場面です。8 枚の机でも動きますが、俯瞰画像が訓練時より混んでいるぶん成功率は下がりえます

## 番号読み取りの改善を試した結果(筆跡を増やす / 要確認トレイからの再学習)

seed 4 の仕分けで「16」が「15」と読まれ(確信度 0.37)要確認トレイに回ったのをきっかけに、読み取りの改善を 2 つ試しました。

1. **筆跡を増やす(v2 レシピ)**: 学習フォントを 8 → 16 種に増やし、字形を崩す変形(せん断・縦横比・なめらかなゆがみ・線の太さ)を足し、紛らわしい数字(1,2,3,5,6,7)を 2 倍作る。`python -m cloth_sort.ml.train --recipe v2`
2. **要確認トレイからの再学習**: パイプラインと dora の brain ノードが、要確認に回した布の切り出しを `review_queue/` に残す。人が `tools/review_label.py` で番号を付けると、`ml/train.py --feedback <dir>` で 1 文字ずつに分けて学習に足せる(`cloth_sort/ml/feedback.py`)。評価では人の代わりに正解の番号を使った(`labeled_by: simulated_human`)

評価は 2 段で行いました。合成した文字 1 つずつ(学習に使っていないフォント 3 種)と、MuJoCo の場面から切り出した布 1 枚単位(別シードの 40 場面・478 枚、`tools/reading_eval.py`)です。
フィードバックには、さらに別の 40 場面(476 枚)で v2 が要確認に回した 157 枚を使い、そのうち文字数が合って使えた 101 枚(166 文字)を足しました。

| モデル | 合成・未見フォント(1 文字) | 場面の布 478 枚: 置き場へ正しく / 誤って / 要確認 |
|---|---|---|
| v1(現行、`models/charnet.pt`) | 84.6% | 323 / **10** / 145 |
| v2(筆跡を増やす) | **97.2%** | 291 / 25 / 162 |
| v1 + 要確認からの再学習 | 90.5% | **374** / 27 / 77 |
| v2 + 要確認からの再学習 | 98.8% | 370 / 22 / 86 |

しきい値を変えて「誤って置く数」をそろえると、どのモデルもほぼ同じ線の上に乗ります(誤り 10 前後で正しく置けるのは 260〜330 枚)。
つまり、(1) は合成の文字では大きく効いたが場面の布では効かず、(2) は要確認を減らす代わりに誤配置を増やしただけで、全体としての改善にはなりませんでした。現行の v1 を既定のまま残しています。

原因を見ると、場面での読み違いのほとんどは文字の分類ではなく文字の切り分けでした。俯瞰カメラは 1 px = 1 mm で、番号の高さは 13〜17 px しかありません。
細い線が二値化で消えたり、「13」の 1 と 3 がくっついて 1 文字になったりして、「13 → 3」「10 → 1」「14 → 1」のように桁が落ちます(478 枚中 69 枚で文字数が合わない)。
二値化を明るさの相対値に変える案も試しましたが、布の織り目まで拾って悪化しました。

効くと考えられる次の手は、文字を大きく撮ることです。つまんだ後に手首カメラで近くから番号を読む、または俯瞰カメラの解像度を上げる(シミュレータの布のテクスチャは 4 px/mm あり、情報は残っている)。

## 講義の技術スタック・推奨との対応

AI アルゴリズムそのものではなく「動かし続けるための基盤」を扱う講座でした。
本リポジトリが講義のどの内容に乗っていて、どこを意図的に変えたかを整理します。

| 講義で扱った内容 | 本リポジトリでの対応 |
|---|---|
| MLOps・RobOps(第1・2回: データ収集 → 学習 → 評価 → 運用のループ) | 実行ログを JSONL で残し、置いた後にカメラで読み直して計画と照合(自己検証)。低確信度は止めずに要確認トレイへ逃がし、人の確認結果を再学習データにできる構造(`ml/feedback.py`、`tools/review_label.py`) |

### 講義の想定と違う点(意図して外したもの)

- 把持は物理に任せたが、置き方は妥協した。布は折れたまま置き場に落ちるので、平らに並べる工程(実機なら治具か人手)は別に要る。剛体 + 吸着版はその限界を持たない代わりに「つかめるか」を検証していない。両方を残して、どちらの限界も報告書に書いた
